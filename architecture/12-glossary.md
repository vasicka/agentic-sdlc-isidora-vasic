# 12. Glossary

This glossary defines the terms used throughout the BankOCR architecture documentation. Terms are listed alphabetically. Where a term has a specific meaning within the kata specification or the BankOCR architecture, that meaning is stated explicitly.

---

| Term | Definition |
|------|-----------|
| **Account number** | A nine-digit number encoded in an input file as nine consecutive ASCII glyphs. Each digit occupies a 3×3 character grid. |
| **Account string** | The nine-character string returned by the Parser after converting one account entry. Each character is either a decimal digit (0–9) or a placeholder for an unrecognised glyph. |
| **ADR (Architecture Decision Record)** | A document that records a single architectural decision, its context, rationale, and consequences. ADRs in this project are stored in `architecture/09-architecture-decisions.md` and are never overwritten once accepted. |
| **arc42** | A template for software and system architecture documentation structured into twelve chapters. Used as the documentation framework for this project. |
| **ASCII glyph** | A digit represented using pipe (`|`), underscore (`_`), and space characters arranged across three rows of three characters each. BankOCR recognises the ten glyphs for digits 0–9. |
| **BankOCR** | The Python 3 CLI application that reads ASCII account number files, recognises digits, validates checksums, and writes annotated results. |
| **BankOCR CLI** | The single deployable unit of the BankOCR system; a command-line Python application invoked with the path to an input file. |
| **C4 model** | A hierarchical notation for software architecture diagrams comprising four levels: Context, Container, Component, and Code. This project uses the Context, Container, and Component levels. |
| **Checksum** | The mod-11 validation formula applied to a nine-digit account number: `(d9 + 2·d8 + … + 9·d1) mod 11`. A result of 0 indicates a valid account number. |
| **CLI (Command-Line Interface)** | The user-facing interface of BankOCR. The User invokes the application from a terminal, providing the input file path as an argument. |
| **Component** | In the C4 model, a named unit of code within a container with a defined responsibility. BankOCR has three components: Parser, Validator, and Processor. |
| **Container** | In the C4 model, a separately deployable or runnable unit within a system. BankOCR consists of a single container: the BankOCR CLI. |
| **Entry** | One account number as it appears in the input file: four consecutive lines comprising three glyph rows and one blank separator line. |
| **ERR** | The status returned by the Validator, and the annotation appended to an output line, when all nine glyphs are recognised but the account number fails the mod-11 checksum. |
| **Glyph** | See *ASCII glyph*. |
| **ILL** | The status returned by the Validator, and the annotation appended to an output line, when one or more glyphs in an account entry cannot be matched to a known digit pattern. |
| **Input file** | A plain-text file provided by the User containing one or more account entries, each occupying four lines (three glyph rows followed by one blank line). |
| **kata** | A coding exercise with a fixed problem statement used for practice and learning. BankOCR implements the Bank OCR kata as defined at [codingdojo.org/kata/BankOCR](https://codingdojo.org/kata/BankOCR/). |
| **Mod-11 checksum** | See *Checksum*. |
| **Output file** | A plain-text file written by BankOCR containing one result line per account entry. Valid account numbers appear without annotation; invalid numbers are suffixed with ` ERR` or ` ILL`. |
| **Parser** | The BankOCR component responsible for receiving a four-line ASCII account entry and converting each 3×3 glyph into a digit character. Returns a nine-character account string. Has no dependency on file I/O. |
| **Pipeline** | The fixed processing sequence applied to each account entry: Parse → Validate → Record. |
| **Placeholder** | A non-digit character inserted by the Parser into an account string at the position of any glyph it cannot recognise. Its presence causes the Validator to return `ILL`. |
| **PlantUML** | A text-based tool for generating diagrams from plain-text descriptions. Used in this project to produce C4 and sequence diagrams stored as `.puml` files, with `.svg` output generated by a pre-commit hook. |
| **Processor** | The BankOCR component responsible for reading the input file, splitting it into entries, coordinating the Parser and Validator, and writing the results file. The only component with file I/O access. |
| **Results file** | See *Output file*. |
| **Standard library** | The collection of modules included with Python 3 and available without installation. BankOCR uses only the standard library at runtime; no third-party packages are required. |
| **unittest** | Python's built-in unit testing framework. Used as the sole testing framework in this project. |
| **User** | The person who provides an ASCII account number file to BankOCR and receives the results file. The only external actor in the system. |
| **VALID** | The status returned by the Validator when all nine glyphs are recognised and the account number passes the mod-11 checksum. The corresponding output line carries no annotation. |
| **Validator** | The BankOCR component responsible for receiving a nine-character account string and returning `VALID`, `ERR`, or `ILL` based on the mod-11 checksum and the presence of any placeholder characters. Has no dependency on file I/O. |
