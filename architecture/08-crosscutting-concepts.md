# 8. Crosscutting Concepts

Crosscutting concepts are design rules and patterns that apply across multiple components rather than belonging to a single one. This chapter documents the concepts that shape BankOCR uniformly throughout the codebase.

---

## 8.1 Error Handling and Result Classification

BankOCR distinguishes three mutually exclusive outcomes for every account entry. This classification is enforced consistently from Parser through Validator to Processor.

| Outcome | Cause | Result line |
|---------|-------|-------------|
| `VALID` | All nine glyphs recognised; checksum passes | Account number, no annotation |
| `ERR` | All nine glyphs recognised; checksum fails | Account number suffixed with ` ERR` |
| `ILL` | One or more glyphs unrecognised | Account number (with placeholders) suffixed with ` ILL` |

**Rules applied across components:**

- The Parser signals an unrecognised glyph by inserting a placeholder character into the account string. It does not raise an exception or return a special object.
- The Validator treats the presence of any placeholder as an `ILL` condition and skips the checksum calculation entirely.
- The Processor maps every Validator result to exactly one output line. No entry is silently dropped.

This approach keeps error propagation explicit and traceable across the pipeline without requiring exceptions for expected input conditions.

---

## 8.2 Separation of I/O from Logic

File I/O is confined to the Processor. The Parser and Validator operate exclusively on strings passed to them as arguments and return values. This boundary is enforced by design, not by a framework.

The practical consequence is that the Parser and Validator can be tested by passing string literals directly, with no file fixtures, temporary directories, or mock objects needed. This directly supports the testability quality goal (Chapter 1, priority 2).

---

## 8.3 Testability Conventions

All components are designed for independent unit testing using `unittest` (TC-5). The following conventions apply across the codebase:

- **Parser tests** pass raw multi-line strings representing one account entry and assert on the returned nine-character account string.
- **Validator tests** pass nine-character strings directly and assert on the returned status (`VALID`, `ERR`, or `ILL`).
- **Processor tests** may use temporary files or in-memory strings to test the coordination logic and output formatting end-to-end.
- No test requires network access, an external service, or a pre-existing file on disk beyond what the test itself creates.

---

## 8.4 Input Format Handling

The four-line entry format (TC-2) is a fixed external constraint. The Processor is solely responsible for reading the file and slicing it into entries. The Parser receives a single pre-sliced entry and assumes the four-line structure has already been validated by the Processor.

This means format errors (e.g. a file with the wrong number of lines) are caught and handled at the Processor level, before data reaches the Parser or Validator.

## 8.5 Coding and Style Conventions

The following conventions apply uniformly across the codebase:

| Convention | Detail |
|-----------|--------|
| Language | Python ≥ 3.12 (TC-1) |
| Line length | 88 characters (`pyproject.toml`, Black default) |
| Formatting | Enforced by Black via pre-commit hook |
| Import ordering | Enforced by isort via pre-commit hook |
| Linting | Enforced by Ruff via pre-commit hook (error, warning, convention, refactor, and import rules) |
| No external runtime dependencies | Only the Python standard library is used (TC-3) |

These conventions are enforced automatically on every commit and do not require manual review.

---

## 8.6 Documentation Conventions

Architecture documentation follows arc42 structure with C4 diagrams rendered from PlantUML source files (OC-2). The following rules apply uniformly:

- Every `.puml` file has a corresponding `.svg` generated by the pre-commit hook and referenced from the relevant Markdown chapter.
- Architectural decisions are recorded as ADRs in `architecture/09-architecture-decisions.md` and are never overwritten once accepted (OC-3).
- Chapter content must remain consistent with approved ADRs and previously approved chapters.
